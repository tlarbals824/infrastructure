# ArgoCD and Cloudflare Access OIDC

## Purpose

This document records the required separation between the Cloudflare Access application that protects ArgoCD and the Cloudflare Access OIDC application used by ArgoCD Dex.

## Correct Architecture

There are two different Cloudflare application roles:

1. **Self-hosted application**
   - Domain: `argocd.<domain>`
   - Protects the ArgoCD web endpoint with Cloudflare Access policies.
   - This is the application represented by `cloudflare_access_application.argocd` with `type = "self_hosted"`.

2. **SaaS OIDC application**
   - Acts as the OIDC identity provider for ArgoCD Dex.
   - Must be created as a Cloudflare Access **SaaS application** with OIDC enabled.
   - Its OIDC client ID and client secret are stored in the ArgoCD Secret.

Do not use a Cloudflare Access Service Token as the Dex OIDC client credential. Service Tokens are for machine authentication to Access-protected resources using `CF-Access-Client-Id` and `CF-Access-Client-Secret` headers. They are not OIDC application credentials.

## Credential Separation

| Value | Used by |
| --- | --- |
| SaaS OIDC client ID and secret | Dex connector `clientID` and `clientSecret` |
| Service Token client ID and secret | Access API or protected-resource requests with Cloudflare headers |
| `argo-cd` | ArgoCD's own OAuth client ID when ArgoCD server calls Dex |

The browser request generated by ArgoCD should look like this:

```text
/api/dex/auth?client_id=argo-cd&redirect_uri=https://argocd.<domain>/auth/callback
```

It must not use the Cloudflare SaaS OIDC client ID in this URL. That ID is used by Dex when Dex redirects to Cloudflare Access.

## Cloudflare OIDC Endpoints

For a Cloudflare team domain and SaaS OIDC client ID, the issuer must be application-specific:

```text
Issuer:
https://<team>.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<oidc-client-id>

Discovery:
https://<team>.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<oidc-client-id>/.well-known/openid-configuration

Authorization:
https://<team>.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<oidc-client-id>/authorization

Token:
https://<team>.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<oidc-client-id>/token

JWKS:
https://<team>.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<oidc-client-id>/jwks
```

The Cloudflare SaaS application must allow this redirect URI:

```text
https://argocd.<domain>/api/dex/callback
```

The final ArgoCD callback is different:

```text
https://argocd.<domain>/auth/callback
```

## ArgoCD Configuration

The Dex connector should use the SaaS OIDC application's credentials:

```yaml
dex.config: |
  connectors:
    - type: oidc
      id: cloudflare-access
      name: Cloudflare Access
      config:
        issuer: https://<team>.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<oidc-client-id>
        clientID: $argocd-cloudflare-access:clientID
        clientSecret: $argocd-cloudflare-access:clientSecret
        insecureEnableGroups: true
        insecureSkipEmailVerified: true
        scopes:
          - openid
          - profile
          - email
```

When a custom Secret is referenced, the generated Secret must have this label:

```yaml
metadata:
  labels:
    app.kubernetes.io/part-of: argocd
```

The encrypted values belong in the SealedSecret only. Never place the plaintext OIDC secret in Git.

## Migration Checklist

1. Create or identify a Cloudflare Access SaaS application with OIDC enabled.
2. Confirm its application-specific discovery URL returns JSON, not `Application is not an OIDC application`.
3. Set the SaaS application's redirect URI to `/api/dex/callback`.
4. Store that SaaS application's client ID and client secret in the SealedSecret.
5. Set Dex `issuer` to the application-specific issuer URL.
6. Sync `infra-argocd` and restart `argocd-dex-server` if the config or Secret was not reloaded.
7. Start login from `https://argocd.<domain>/auth/login` or the ArgoCD root page. Do not construct `/api/dex/auth` URLs manually.

## Validation

Check the OIDC discovery document:

```bash
curl -fsS \
  "https://<team>.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<oidc-client-id>/.well-known/openid-configuration" \
  | jq '{issuer, authorization_endpoint, token_endpoint, jwks_uri}'
```

Check ArgoCD and Dex:

```bash
kubectl -n argocd get application infra-argocd
kubectl -n argocd logs deployment/argocd-dex-server --since=10m
```

For an internal route test, `/api/dex/auth` has no trailing slash:

```text
/api/dex/auth       -> expected redirect
/api/dex/auth/      -> 404 on the current ArgoCD server
```

## Known Failure Signatures

- `Invalid client_id`: a Cloudflare OIDC client ID was sent to Dex. The initial ArgoCD request should use `client_id=argo-cd`.
- `404 page not found` for `/api/dex/auth/`: the endpoint has an extra trailing slash.
- `Application is not an OIDC application`: the Cloudflare application behind the issuer URL is a self-hosted application, not a SaaS OIDC application.
